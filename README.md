# Hikvision → Phoenix

**2026-09-26 — new path (production):** the terminal pushes to the cloud
`hikvision-ingest` service (`ingest_server.py` + `hik_parser.py`), which sends the
scans to the intranet's staff **Tabel** — and, optionally (`EMPLOYEE_URL`), to the Phoenix Employee
app for check-in / check-out. No computer at the school, no attendance rules here — the receivers
decide what a scan means. Setup and
the pilot: **[DEPLOY.md](DEPLOY.md)**. Tests: `.venv/bin/python -m unittest discover -s tests -t .`

`hik_parser.py` is the parser of `webhook_server.py`, moved without changing its
behaviour; `tests/test_parser_parity.py` keeps the two identical.

**Everything below describes the legacy laptop server `webhook_server.py`**
(Telegram only). It keeps running during the pilot and is switched off after it.

# Hikvision → Telegram, через httpHosts push

Терминал сам отправляет события на сервер. Устройство может повторно прислать
старые события, поэтому сервер проверяет исходную дату каждого прохода. Пока
терминал разгружает старые события, сервер каждые пять секунд отдельно читает
новые успешные проходы из журнала устройства через ISAPI.

## Установка

```bash
pip install -r requirements.txt
```

## Шаг 1 — впиши настройки

В **обоих** файлах (`webhook_server.py` и `configure_httphost.py`) укажи:
- `TELEGRAM_BOT_TOKEN` (только в webhook_server.py)
- `TELEGRAM_ADMIN_CHAT_IDS` (только в webhook_server.py)
- `DEVICE_IP` / `DEVICE_USER` / `DEVICE_PASS` (только в configure_httphost.py, уже вписаны)

## Шаг 2 — запусти сервер, который будет принимать события

```bash
python webhook_server.py
```

Оставь его работать (в отдельном терминале/окне). Он слушает
`http://0.0.0.0:5002/webhook`.

## Шаг 3 — скажи терминалу слать события сюда

В **новом** терминале запусти:

```bash
python configure_httphost.py
```

Скрипт сам определит IP твоего компа в локалке и пропишет его в
настройки устройства через ISAPI. Если определит неверно (например,
на компе несколько сетевых интерфейсов) — впиши `WEBHOOK_IP` руками
в файле.

## Шаг 4 — тест

Подойди к терминалу, пройди идентификацию лицом и паролем. В окне с
`webhook_server.py` должно появиться:
```
[EVENT] 🚪 Вход — Door1
```

В Telegram придёт сообщение + фото только если выполнены все условия:

- это проход зарегистрированного сотрудника: терминал передал имя и табельный ID;
- событие пришло от `Door1` (или двери с номером `1`);
- терминал прислал событие `Combined Authentication Passed` — успешное
  подтверждение лица и пароля.

Системные события, тревоги, нераспознанные лица и простое появление человека
в кадре в Telegram не уходят. События старше двух минут, с отсутствующим
временем или временем из будущего также игнорируются и не меняют учёт
входа/выхода. Получение одной записи и через webhook, и через журнал не
создаёт дубликат уведомления. Терминал не передаёт отдельный статус входа или
выхода, поэтому направление определяется по местному времени самого прохода:
с 05:00 до 14:59 — вход, с 15:00 до 04:59 — выход. Даже если утренний
проход сотрудника пропущен, вечерний не будет ошибочно отмечен как вход.
Повторные пакеты одного прохода за 90 секунд игнорируются. Состояние
дедупликации сохраняется в локальном файле `attendance_state.json`, поэтому
не теряется после перезапуска сервера.

Для входа бот покажет, вовремя ли пришёл сотрудник или на сколько минут
опоздал; для выхода — вовремя ли ушёл или на сколько минут ушёл раньше.
Выход после полуночи не считается ранним уходом относительно следующего дня.

Терминал определён по IP `192.168.0.141`; его системный `deviceID=255`,
а основной видеоканал — `101`. В webhook-пакетах внутренний ID отличается,
поэтому для фильтрации источника используется IP терминала. Распознавание только
лица не отправляется. Фото берётся из того же запроса или из записи журнала
терминала с совпадающими сотрудником и временем события. Отдельное фото без
идентификатора события не используется: его можно ошибочно прикрепить к другому
человеку. Если фото не удалось точно сопоставить, приходит только текст.

Для DS-K1T331W это событие приходит в webhook внутренним кодом `153` (в панели
оно отображается как `Combined Authentication Passed`). Другие коды, включая
обычное распознавание лица, игнорируются.

Рабочий день задаётся в `webhook_server.py` константами `WORKDAY_START` и
`WORKDAY_END` (сейчас `14:00`–`20:00`); окна определения направления —
`ENTRY_WINDOW_START` и `EXIT_WINDOW_START` (сейчас `05:00` и `15:00`).
Укажи фактический график до запуска. Правило по времени не умеет отличить
ночную смену или нестандартный график: для них нужны отдельные настройки
сотрудников либо явный статус входа/выхода от терминала.

## Важно

- Комп с `webhook_server.py` должен быть **постоянно включён и в той
  же сети**, что и терминал, пока идёт тест/прод — иначе события
  могут быть доставлены с задержкой или повторно. Сервер не отправит в Telegram
  события старше двух минут.
- Порт 5002 — дефолт для теста. Для продакшена вынеси сервер на
  постоянную машину/сервер и рассмотри HTTPS + аутентификацию
  (`httpAuthenticationMethod` можно сменить с `none` на `digest` —
  тогда терминал будет добавлять Digest-заголовок к своим запросам).

## Перенос персональных PIN на новый терминал

`migrate_pins.py` использует настройки двух устройств из `migration_fixed.py`.
Сначала убедись, что на новом терминале включён режим **Device-Set Personal
PIN**, а не Platform-Applied Personal PIN. Скрипт не создаёт сотрудников и
отправляет изменение только для существующей записи, сохраняя её имя, права и
режим проверки. После каждого обновления он повторно читает запись и сверяет
PIN и основные поля. Если табельный ID или имя не совпадают, сотрудник будет
пропущен. PIN в вывод и файлы не записываются.

```bash
python3 migrate_pins.py
```

Это только просмотр: какие записи готовы к переносу. Затем перенеси одного
сотрудника, указав его точный табельный ID:

```bash
python3 migrate_pins.py --apply --employee-no 19
```

Проверь на терминале реальный проход **лицо + прежний PIN** этого сотрудника.
Только после успешной проверки перенеси остальных:

```bash
python3 migrate_pins.py --apply --all --pilot-id 19 --confirm-bulk
```

Пилот должен уже иметь совпадающий PIN на новом терминале. Скрипт не
перезаписывает существующие отличающиеся PIN и останавливается при первой
ошибке записи или проверки. Как и `migration_fixed.py`, он выдерживает не
меньше 30 секунд между началом обработки соседних сотрудников. При `401`
останавливается без повторных попыток; после восстановления доступа повторный
запуск пропустит уже перенесённые PIN. Запись с ID `1` по умолчанию пропускается:
имена на двух устройствах различаются. Если ответственный подтвердил, что
табельный ID `1` принадлежит одному и тому же человеку, допускается отдельный
перенос только этой записи:

```bash
python3 migrate_pins.py --apply --employee-no 1 --allow-name-mismatch
```

Флаг нельзя использовать с `--all`; он не меняет имена и не затрагивает
другие записи.
